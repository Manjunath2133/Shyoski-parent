# SHYOSKI PHASE 11 IMPLEMENTATION REVIEW

## 1. Phase 11 Overview
Phase 11 introduces a centralized, tenant-aware, and role-aware Notification System for the Shyoski V2 backend platform. Notifications are database-backed, read-efficient, and generated automatically from service-level business events.

---

## 2. Architectural Decisions

### A. Service-Layer Event Generation
* **Decision**: Encapsulated notification generation inside service layers rather than Hono router controller handlers.
* **Details**: Existing services (`InvitationService`, `MembershipService`, `EnrollmentService`, `SubmissionService`, `GroupService`, `PaymentService`, `CertificateService`) now trigger `NotificationService.createNotification` inside their operations. This ensures that no matter how an action is triggered (REST API, background jobs, webhooks), notifications are emitted consistently.

### B. Index & Performance Optimizations
* **Decision**: Configured index optimizations and resolved serverless connection pool hanging issues in local development.
* **Details**:
  * Optimized user feed queries using compound indexes: `{ uid: 1, isRead: 1, createdAt: -1 }` and `{ uid: 1, createdAt: -1 }`.
  * Implemented conditional connection cleanup: added a Hono middleware to invoke `closeDb()` post-request *only* when `ENVIRONMENT === 'development'`. This cleanly releases persistent socket resources in Miniflare local testing while preserving connection pooling and preventing TLS handshake/connection churn in production.
  * Restored background database index creation check in `getDb()` *only* for non-development (production/staging) environments, ensuring fresh production deployments automatically set up index structures on first load. In development, index creation is offloaded to `/test-db` or tests.

### C. Soft Retention & Severity Mapping
* **Decision**: Standardized notification documents schema with soft-archiving (`isArchived`, `archivedAt`) and severity levels (`success` | `info` | `warning` | `error`) to facilitate frontend presentation rules.

---

## 3. Security Review

### A. Tenant Boundary & Identity Isolation
* **Vulnerability Avoided**: Cross-tenant data leakage where user A could view notifications of user B.
* **Solution**: User notifications feed (`GET /api/v2/notifications` and `/unread-count`) extracts the user identity (`actor.uid`) directly from the verified Firebase authentication token context. Users can never query records belonging to other UIDs.

### B. Ownership Verification on Mutator Actions
* **Vulnerability Avoided**: Unauthorized users marking someone else's notification as read.
* **Solution**: The `PATCH /api/v2/notifications/:id/read` endpoint performs a strict ownership match in the update query: `{ _id: new ObjectId(notificationId), uid }`. Attempting to read another user's notification is rejected with a `404 Not Found` response.

### C. Retry Idempotency & Deduplication
* **Vulnerability Avoided**: Duplicate notifications generated by network retries, webhook replays, or double-clicks.
* **Solution**: Added `eventKey` string values to business events (e.g. `PAYMENT_CAPTURED:payment_123`) backed by a unique sparse index on `{ uid: 1, eventKey: 1 }`. Duplicate insertion attempts are silently ignored (`code 11000`), keeping the feed deduplicated.

---

## 4. Known Limitations
* **Connection Re-establishment Cost in Local Dev**: Closing connections in development middleware forces a reconnect on subsequent requests. This adds latency to local runs in Miniflare but is necessary to prevent local socket hangs. In production, Cloudflare connection pooling maintains connections across requests, so there is no extra connection overhead or Atlas churn.
