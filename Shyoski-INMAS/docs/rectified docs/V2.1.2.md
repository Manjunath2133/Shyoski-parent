# SHYOSKI ARCHITECTURE CLARIFICATIONS V2.1.2

## 1. Student-to-Batch Mapping

Decision:

Students must NOT use batch_assignments.

Create dedicated collection:

batch_enrollments

Purpose:

Represents student participation in a batch.

Schema:

{
_id,
organizationId,
batchId,
uid,
enrollmentStatus,
joinedAt,
completedAt
}

Status Values:

active
completed
dropped
suspended

Reason:

Mentors and evaluators are assigned.

Students are enrolled.

These are different business concepts.

---

Relationship Model

organization_memberships

Determines:

User belongs to organization

---

batch_enrollments

Determines:

User participates in batch

---

batch_assignments

Determines:

Mentor/evaluator assigned to batch

---

## 2. Organization Invitations Ownership

{

email,
role,
token,
status,
expiresAt,

}

## 3. Certificate Verification For Suspended Organizations

Decision:

Verification MUST continue.

Example:

ABC Certifications leaves platform.

Organization Status:

archived

Result:

No New Batches

No New Payments

No New Certificates

No New Enrollments

BUT

Existing certificates remain valid.

---

Verification Page Displays:

Certificate Status

Organization Status

Example:

Certificate:
VALID

Organization:
ARCHIVED

Reason:

A student's achievement remains valid.

Organization departure must not invalidate earned certificates.

---

Revoked Certificate

Certificate Status:
REVOKED

Always overrides organization status.

Example:

Certificate:
REVOKED

Organization:
ACTIVE

Result:

Certificate invalid.

---

Verification Logic Priority

1. Certificate Exists

2. Certificate Status

3. Organization Status

Certificate status always wins.

---

## 4. Submission And Group Validation

Decision:

Every batch operation must validate enrollment.

---

Submission Validation

Before accepting submission:

Verify:

batch_enrollments

WHERE

uid = currentUser

AND

batchId = targetBatch

AND

enrollmentStatus = active

If not found:

403 Forbidden

Not enrolled in batch.

---

Group Creation Validation

Before creating group:

Verify:

Active batch enrollment exists.

---

Group Join Validation

Before joining group:

Verify:

Active batch enrollment exists.

Verify:

Same batch.

Verify:

Group member limit not exceeded.

---

Group Submission Validation

Before accepting group submission:

Verify:

All group members belong to same batch.

Verify:

All group members active.

Verify:

Group exists.

Verify:

Submitting member belongs to group.

---

Backend Security Rule

Frontend membership state is never trusted.

Every critical action must re-validate:

1. User Identity
2. Organization Membership
3. Batch Enrollment
4. Role Permissions

Server-side only.
