



# SHYOSKI V2.3 EDGE CASES & BUSINESS RULES

# CORE PRINCIPLE

When a business rule is ambiguous:

Priority Order:

1. Data Integrity
2. Security
3. Payment Accuracy
4. Certificate Validity
5. User Experience

Never sacrifice security or data integrity for convenience.

---

# USER RULES

## Case: Same Email Registers Twice

Rule:

Reject registration.

Email must be globally unique.

---

## Case: User Changes Email

Rule:

Allowed.

Must update Firebase and MongoDB.

Existing certificates remain valid.

Historical records remain attached to uid.

---

## Case: User Changes Name

Rule:

Allowed before certificate issuance.

After certificate issuance:

Name change does NOT modify existing certificates.

Future certificates use updated name.

---

## Case: User Account Deleted

Rule:

Soft delete only.

Never physically remove user records.

Reason:

Certificates must remain verifiable.

Audit logs must remain intact.

---

# ORGANIZATION RULES

## Case: Organization Deleted

Rule:

Never hard delete.

Status becomes:

suspended

or

archived

All data preserved.

---

## Case: Organization Suspended

Rule:

Students can view history.

No new enrollments.

No new payments.

No new certificates.

---

## Case: Organization Logo Changed

Rule:

New certificates use new logo.

Previously issued certificates keep original logo snapshot.

---

## Case: Organization Admin Removed

Rule:

Must ensure at least one org admin remains.

System blocks removal of last admin.

---

# MEMBERSHIP RULES

## Case: Student Joins Multiple Organizations

Rule:

Allowed.

No limit in V2.

---

## Case: Student Has Different Roles Across Organizations

Example:

Org A -> Student

Org B -> Mentor

Rule:

Allowed.

Role is organization-specific.

---

## Case: Membership Removed

Rule:

Future access revoked.

Historical submissions remain.

Historical certificates remain.

Historical payments remain.

---

# BATCH RULES

## Case: Student Enrolls Twice

Rule:

Prevent.

Unique constraint:

batchId + uid

---

## Case: Batch Full

Rule:

Reject enrollment.

Return meaningful error.

---

## Case: Batch Archived

Rule:

Read-only mode.

No new submissions.

No payments.

No enrollment.

---

## Case: Batch Start Date Not Reached

Rule:

Student can view batch.

Cannot submit work.

---

## Case: Batch Ended

Rule:

Submissions locked.

Unless extension granted.

---

# SUBMISSION RULES

## Case: Student Submits Multiple Times

Rule:

Keep latest submission.

Store revision history.

---

## Case: Evaluator Rejects Submission

Rule:

Student may resubmit.

Submission status:

rejected

---

## Case: Evaluator Approves Then Changes Mind

Rule:

Allowed.

Creates audit log.

Reason mandatory.

---

## Case: GitHub Link Invalid

Rule:

Submission accepted.

Evaluator decides approval.

System does not validate repository quality.

---

## Case: GitHub Repository Becomes Private

Rule:

Evaluator may reject.

Student must resubmit.

---

# GROUP RULES

## Case: Group Creator Leaves

Rule:

Ownership transferred automatically.

Oldest member becomes leader.

---

## Case: Group Exceeds Member Limit

Rule:

Reject join request.

---

## Case: Student Leaves Group After Submission

Rule:

Locked.

Cannot leave group after Week 3 submission.

---

## Case: Group Deleted

Rule:

Only if:

No approved submissions.

Otherwise archive only.

---

## Case: Duplicate Group Names

Rule:

Allowed.

GroupCode remains unique.

---

# CHAT RULES

## Case: Message Deleted

Rule:

Soft delete.

Audit record retained.

---

## Case: Offensive Content

Rule:

Future moderation system.

Flag mechanism reserved.

---

## Case: Spam Messages

Rule:

Rate limiting.

Example:

30 messages per minute.

---

# PAYMENT RULES

## Case: Payment Success But Verification Fails

Rule:

Status:

pending_verification

Retry verification.

Never issue certificate automatically.

---

## Case: Payment Success But DB Update Fails

Rule:

Webhook retry.

Certificate generation blocked.

---

## Case: Duplicate Payment

Rule:

Mark duplicate.

Escalate for review.

No duplicate certificate.

---

## Case: Refund Issued

Rule:

Certificate status:

revoked

---

## Case: Payment Gateway Timeout

Rule:

Status:

pending

Allow reconciliation later.

---

# CERTIFICATE RULES

## Case: Generate Certificate Twice

Rule:

Return existing certificate.

Never create duplicate certificate numbers.

---

## Case: Certificate Revoked

Rule:

Verification page shows:

Certificate Revoked

Reason displayed.

---

## Case: Student Changes Name After Certificate

Rule:

Certificate remains unchanged.

Verification still succeeds.

---

## Case: Certificate Link Shared Publicly

Rule:

Allowed.

Verification endpoint is public.

---

## Case: QR Code Scanned 1 Million Times

Rule:

Verification remains public.

Implement caching.

---

# JOB RULES

## Case: Job Closed

Rule:

Applications disabled.

History preserved.

---

## Case: Student Already Applied

Rule:

Prevent duplicate application.

---

## Case: Organization Removed

Rule:

Jobs archived.

---

# SECURITY RULES

## Case: User Modifies API Payload

Rule:

Never trust payload role.

Role verified server side.

---

## Case: User Modifies organizationId

Rule:

Ignore frontend organizationId.

Resolve from membership.

---

## Case: User Calls Admin API Directly

Rule:

RBAC validation.

Return 403.

---

## Case: JWT Expired

Rule:

401 Unauthorized.

Force re-authentication.

---

# AUDIT RULES

Audit entry required for:

Organization Created
Organization Updated
Batch Created
Batch Updated
Submission Reviewed
Membership Removed
Payment Verified
Refund Issued
Certificate Generated
Certificate Revoked

Audit logs immutable.

Never editable.

Never deletable.

---

# SCALING RULES

## Case: 10,000 Concurrent Users

Rule:

Use pagination.

No full collection scans.

---

## Case: 100,000 Students

Rule:

Indexes mandatory.

---

## Case: 1,000,000 Chat Messages

Rule:

Archive old chats.

---

## Case: MongoDB Unavailable

Rule:

Graceful failure.

No partial writes.
